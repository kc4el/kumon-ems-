1. [HIGH] `ExpenseClaim` views orphaned — `core/views.py:415-422` (`ExpenseClaimListCreateView`, `ExpenseClaimDetailView`) have **no route** in `api/urls.py:1-111` (only `claim-statuses/` + `messages/` wired). Model + serializer ship dead; any client hits 404. Either wire routes or delete views.

Typos/UUID-vs-text mismatch silently orphan; deleting an `ExpenseClaim` leaves `ClaimStatus` rows; no cascade, no join, dual status sources (`ExpenseClaim.status` vs `ClaimStatus.status`) can disagree.
3. [HIGH] `ClaimStatus` POST is upsert-blind — `core/views.py:406-412` ignores `validated_data`, re-reads raw `request.data`, and `update_or_create` on `claim_id=None` collapses all missing-id POSTs onto one `NULL`-ish row; `serializers.py:178` strips the uniqueness validator (`extra_kwargs validators=[]`) so duplicate POST returns 200-upsert instead of 400/409; concurrent same-`claim_id` POSTs race past `update_or_create` into `IntegrityError` → 500 (no `transaction.atomic`, no `IntegrityError` map). `status` is free text, no choices — any string persists.
4. [MED] `Message.validate` KeyErrors off-request — `core/serializers.py:165-170` indexes `self.context["request"]` directly; serializer use without request context (shell, signals, tests) raises `KeyError`, not `ValidationError`. `.FILES.get("attachment")` also assumes multipart context.
