## Architecture / proposed approach

Two tiny models (`UserSetting` OneToOne to `User`; `SiteSetting` key-value, staff-only write) plus two endpoints (`settings/me/`, `settings/site/`) under existing `IsAuthenticated`/`IsAdminUser` gates, and one `view-settings` tab slotted into the existing sidebar/`switchView`/breadcrumb pattern. Per-user page size is enforced by a 15-line custom pagination class that reads `UserSetting`; muted notification kinds are enforced in the bell/list queries; `SiteSetting` values are read by code that today hardcodes them (purge default days, onboarding cap) so the setting is the source of truth, not a label.

- `IsAdminUser` (is_staff) vs HR-door semantics (`_is_hr_user`): site settings use is_staff = same gate as Django admin; confirm with user if HR role differs.
- Open: should staff see *whose* settings changed? Cheap later via existing `EmployeeAuditLog` signal on `SiteSetting` — suggested, not in v1.
- Open: password change kills other sessions — confirm desired, else drop session-flush from scope.
